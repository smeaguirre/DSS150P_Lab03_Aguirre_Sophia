1. Parquet is the most space-efficient format. At just 5.9 MB, it takes up about a third of the space of PostgreSQL (16.6 MB) and CSV (18.2 MB). It achieves this by storing data in columns and using strong compression, which works incredibly well for repeated words like status or brand names. JSON Lines is the largest format at 35.2 MB—nearly double the size of CSV—because it has to repeat the column names on every single line.
2. Parquet is the fastest for reading the entire dataset, but it isn't best for everything. It reads the full dataset in just 0.125 seconds, easily beating CSV, Postgres, and JSON. However, reading the whole table at once isn't how databases are usually used. If you need to look up a specific row, update records, or have multiple users making changes at the same time, a database like Postgres is the better choice because Parquet isn't built to handle those specific tasks.
3. Parquet is currently faster at filtering, but Postgres can be easily sped up. When searching for specific data, Parquet took 0.034 seconds while Postgres took 0.108 seconds. This happens because Parquet keeps a summary of the data in each section, allowing it to instantly skip chunks of the file that don't match the search. Right now, Postgres is checking every single row to find a match. If you added an "index" to the Postgres database—which works like a roadmap for the data—Postgres would likely become much faster than Parquet for these kinds of searches.
4. JSON Lines is much better than standard JSON for continuously adding new data. If you use a standard JSON array, the computer has to read the entire file, find the closing bracket at the end, and rewrite the structure just to add one new item. With JSON Lines, every record sits on its own line. This means the system can simply attach new data to the very bottom of the file without needing to load or rewrite the rest of the document.
5. Organizing data by overly specific details will slow down your system. If you partition your data by something unique like an order ID or a customer ID, the system will create thousands of tiny files with only a few rows in each. The computer will spend so much time just opening and managing all these little files that it defeats the purpose of organizing the data in the first place. It is much more efficient to group data into larger chunks, like by month or year.
